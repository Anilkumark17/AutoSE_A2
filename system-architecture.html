What the system does

Python-Markdown converts one Unicode Markdown string into one HTML string. A Markdown object builds a fixed five-stage pipeline. Each stage is an ordered list of small processor objects. Extensions plug new processors into those lists. Nothing else in the core changes.

5 stagespre → block → tree (+inline) → serialize → post
5 registriesevery stage held in a util.Registry
18 built-in extensionsall loaded via entry points in pyproject.toml
0 runtime depsstandard library only (xml.etree, html.parser)

1 · Overall system architecture

Solid arrows carry the document. Dashed arrows show control and side channels. Click a box for a short explanation.

Click any box in the diagram.
Main entry point

markdown.markdown(text, **kw) creates a Markdown and calls convert(). The CLI in __main__.py wraps the same path.

Core engine

Markdown builds every stage in build_parser(), loads extensions, then convert() runs stages in fixed order.

Preprocessors

Clean the raw lines. HtmlBlockPreprocessor cuts out raw HTML blocks and leaves placeholders.

Block parser

Splits text into blocks. Asks each BlockProcessor by priority: first to accept builds tree nodes.

Tree processors

Walk and change the element tree. The inline processor is the one that runs inline patterns.

Inline processing

Regex patterns turn text inside elements into links, code spans, emphasis and so on.

Postprocessors

Work on the final string. Put stashed raw HTML back. Restore &.

HTML output

Serializer writes HTML or XHTML. Core strips the wrapping <div>. Output is not sanitized.

Extension system

Each extension adds, replaces or removes processors in the registries. Core never imports a specific extension.

Verified facts behind the diagram

  • CODEMarkdown.convert() runs: preprocessors → parser.parseDocument() → tree processors → serializer → strip <div> → postprocessors (core.py).
  • CODEDefault priorities: preprocessors normalize_whitespace 30, html_block 20; tree inline 20, prettify 10, unescape 0; post raw_html 30, amp_substitute 20.
  • CODEA tree processor may return a new root. convert() swaps it in when the return value is not None.
  • CODEInline patterns reach the stage list only through the inline tree processor. Some inline patterns look it up by name: md.treeprocessors['inline'].stashed_nodes.
  • CODEExtensions register at chosen priorities, for example toc tree 5, attr_list tree 8, abbr tree 7, fenced_code_block pre 25, footnotes in four stages.

Each card shows the documented story as Before → Problem → Decision → After → Trade-offs, then answers the questions with tagged evidence.

ADR-1 · Replace homegrown OrderedDict with purpose-built Registry

Strong architectural decision
BeforeHome-grown OrderedDict; items placed with position strings like "<reference".
ProblemExtensions must insert between built-ins, remove or replace them. Position strings make that relative and fragile.
DecisionOne Registry: register(item, name, priority), deregister(name). Higher runs first.
AfterAll 5 stages use the same structure. Order is a number, lookup is a name.
Trade-offsPriority numbers become an unwritten public API. Re-registering a name loses the old item.
Previous approach and its problem
  • ADREarlier design used a home-grown OrderedDict with relative positions such as "<reference". Cites commit 6ee07d2.
  • ADRThe need: extensions must slot processors between built-ins (footnote inline pattern before reference links) and remove or replace built-ins.
  • INFERENCEThe ADR does not spell out a concrete failure of the old scheme. A relative-position scheme means an item's place depends on another item existing, so removing one can break another's placement. That is my reading, not a documented incident.
How Registry works and why it improves the architecture
  • CODERegistry keeps a dict name→item plus a list of (name, priority). It sorts lazily, high to low, only when read after a change.
  • CODERead like a list: iterate, len(), index by int, by name, or by slice. in works with a name or an instance.
  • CODEregister() with an existing name deregisters the old item first. The docstring warns the old item is lost and position is not kept.
  • CODEderegister(name, strict=True) raises ValueError for unknown names; strict=False fails silently.
  • CODEUsed by all five stages: md.preprocessors, md.parser.blockprocessors, md.inlinePatterns, md.treeprocessors, md.postprocessors. tests/test_apis.py has a RegistryTests class.
  • INFERENCEImprovement: placement becomes absolute. An extension states "run at 175" without depending on any neighbour being present. One mechanism for five stages means one thing to learn.
Trade-offs
  • ADRPriorities are a de-facto public API; changing a built-in priority can silently reorder extensions.
  • CODEEqual priorities are not rejected. Python's stable sort keeps registration order for ties, so extension load order decides. Docstring does not mention ties.
  • INFERENCENothing documents the full priority map in one place; each module declares its own numbers. Finding a free slot means reading several files.
  • INFERENCEOrder bugs fail quietly: wrong order gives wrong HTML, not an error.
Does it make sense?

INFERENCEYes. The structure is small (about 140 lines), generic, tested, and matches what extensions need: name, order, replace, remove. Its main weakness, numeric priorities as hidden contract, is the normal cost of any priority-based plugin system and is called out by the ADR itself.

ADR-2 · Refactor Extension loading

Reasonable decision with trade-offs
BeforeShort names special-cased to modules in markdown.extensions or named mdx_*.
ProblemUsers want short names like 'toc'. Special cases treat built-in and third-party extensions differently.
Decisionbuild_extension(): entry point → module:Class → module.makeExtension().
AfterBuilt-ins are entry points in pyproject.toml, same as third-party. Core imports no extension.
Trade-offsShort names need installed package metadata. Name clashes resolve to first found, silently.
How loading worked, and the problem
  • ADRPreviously short names were special-cased to modules inside markdown.extensions or modules named mdx_*. Cites commit cd73243.
  • ADRContext: users want to enable extensions by short names such as 'toc'.
  • INFERENCENaming conventions baked into core give built-ins a privileged path and force third parties to follow a naming rule. The ADR implies this; it does not quote a bug report.
How the new mechanism works
  • CODEregisterExtensions() accepts Extension instances or strings. Strings go to build_extension(name, configs). Anything else that is not None raises TypeError.
  • CODEbuild_extension() order: (1) entry point in group markdown.extensions, first match wins; (2) path.to.module:ClassName; (3) path.to.module plus its makeExtension(**configs).
  • CODEutil.get_installed_extensions() is wrapped in @lru_cache, so metadata is scanned once per process.
  • CODEAll 18 built-ins are listed under [project.entry-points.'markdown.extensions'] in pyproject.toml.
  • CODEBase Extension: options in config = {'key': [default, 'description']}; unknown keys raise KeyError; bool options pass through parseBoolValue; extendMarkdown(md) must be overridden.
Extensibility and maintainability gains
  • ADRBuilt-in and third-party extensions load the same way; core never imports a specific extension.
  • CODEcore.py imports only from .extensions import Extension (the base class).
  • INFERENCEUses Python's standard plugin mechanism instead of a custom one. A third-party package becomes a first-class short name just by declaring an entry point.
  • INFERENCEDependency direction is clean: extensions → core, never back. That keeps core testable without any extension.
Trade-offs
  • ADRA new built-in needs both a module with makeExtension and an entry point. Short names work only after install.
  • CODEIf two distributions register the same name, entry_points[0] is used. No warning is logged.
  • CODEThe entry-point path calls the loaded object with configs directly; the Extension type check happens later, in registerExtensions().
  • INFERENCEThree lookup paths mean three ways to fail. Error messages differ per path (ImportError vs AttributeError text), which can confuse users.
  • INFERENCERunning from a source tree without pip install -e breaks short names. The README for this experiment installs first for that reason.
Does it make sense?

INFERENCEYes, with caveats. Entry points are the idiomatic Python plugin choice and remove the built-in/third-party split. The cost is reliance on packaging metadata and silent first-wins clashes. Those are acceptable for a library, but a warning on duplicate names would be cheap insurance.

ADR-3 · HTML preservation using HtmlStash

Reasonable decision with trade-offs
BeforeRaw HTML sits inside Markdown text. No earlier design is documented.
ProblemTree text is escaped on output, and Markdown rules would rewrite the author's HTML.
DecisionCut HTML out early, store in md.htmlStash, leave STX/ETX placeholder, swap back after serialization.
AfterAuthor HTML passes through byte-for-byte. Any stage can inject finished HTML.
Trade-offsPlaceholders leak into element text; shared mutable state; restore depends on ordering.
What problem raw HTML introduces
  • ADRThe document is an ElementTree whose text the serializer escapes. Raw HTML must reach output unchanged and must not be parsed as Markdown.
  • CODEconvert() serializes the whole tree before postprocessors run, so any < left in element text would come out as &lt;.
  • ADRThe ADR marks its own "before" and alternatives as inferred: no commit or comment records them. This page treats them the same way.
How the three parts work together
  • CODEHtmlStash.store(html) appends to rawHtmlBlocks and returns HTML_PLACEHOLDER % n = STX + "wzxhzdk:n" + ETX.
  • CODEHtmlBlockPreprocessor (priority 20) feeds the whole source to HTMLExtractor, which calls md.htmlStash.store() for each raw block.
  • CODENormalizeWhitespace (priority 30, runs first) removes STX and ETX from user input, so a user cannot forge a placeholder.
  • CODERawHtmlPostprocessor (priority 30) replaces <p>PLACEHOLDER</p> or bare placeholders. Block-level HTML loses the <p> wrapper. Keys ≥ html_counter are left as-is. Substitution is recursive, so nested placeholders resolve.
  • CODEOther users of the stash: inline html/entity patterns, fenced_code, codehilite, smarty, md_in_html; toc reads it to build plain-text labels.
Why a stash instead of the element tree
  • ADR (inferred alternatives)Parsing HTML into the tree would let the serializer rewrite the author's markup. Leaving it in element text would get it escaped.
  • INFERENCERaw HTML can be malformed or partial (an opening tag in one block, closing in another). ElementTree cannot hold that. An opaque string can.
  • INFERENCEA placeholder is plain text, so every Markdown processor ignores it for free. No processor needs to know HTML exists.
Benefits and limitations
  • ADRBenefit: any stage can inject finished HTML with store(). Cost: code that reads element text (e.g. toc labels) must tolerate placeholders.
  • CODEmd_in_html edits htmlStash.rawHtmlBlocks directly by index (pop then insert(index, '')) to keep later indices valid. That bypasses the stash API.
  • CODEHtmlStash.reset() clears html_counter and rawHtmlBlocks only. tag_counter and tag_data are not reset, and store_tag() has no caller inside the package.
  • CODEconvert() docstring warns: output is not sanitized. Stashed HTML passes straight through.
  • INFERENCEThe stash is a global side channel on md. Correctness depends on index stability and on raw_html running before anything that would alter placeholders.
Does it make sense?

INFERENCEYes as a core idea; the alternatives the ADR lists both lose the author's markup. The weak spot is enforcement, not the concept: the stash's internal list is public, one built-in extension edits it by index, and part of its state is not reset. Rated "reasonable with trade-offs" rather than "strong" for that reason.

4 · How the ADRs relate

Each ADR owns one concern. Together they define how the pipeline is built, who may change it, and how foreign content survives it.

Component management

ADR-1. One ordered, named container per stage. Foundation for the other two.

Extension management

ADR-2. Finds and builds extensions. Their only job is to edit ADR-1 registries.

Data preservation

ADR-3. A side channel around the pipeline, whose correctness depends on ADR-1 order.

INFERENCECollective effect: a closed core with an open edge. Core code stays fixed; all variation enters as registered processors or stashed strings. The price is that ordering (numbers) and placeholders (strings) become the real contracts, and neither is checked by the type system.

5 · What an engineer should be careful about

Five ways to break the design. Each looks harmless and passes a quick test.

Breaking Registry behavior

Example: changing register() so a duplicate name keeps the old position, or reversing the sort.

Why it hurts: extensions rely on "same name replaces" and "higher number first". tests/test_apis.py pins this behaviour.

Bypassing extension loading

Example: importing markdown.extensions.toc inside core.py, or adding a built-in module without its pyproject.toml entry point.

Why it hurts: breaks the extensions-to-core dependency rule; the short name will not resolve.

Breaking raw HTML preservation

Example: putting "<span>" into element.text, removing the STX/ETX strip in NormalizeWhitespace, or forgetting htmlStash.reset().

Why it hurts: HTML gets escaped, users can forge placeholders, or a stale stash leaks between documents.

Incorrect processor order

Example: registering a tree processor that reads link text at priority 25, above inline (20).

Why it hurts: it sees raw [text](url) instead of <a>. Likewise toc (5) must stay after attr_list (8) so custom ids win.

Violating component responsibilities

Example: doing inline regex work inside a block processor, or editing the HTML string in a tree processor.

Why it hurts: each stage assumes a data shape: lines, tree, or string. Work in the wrong stage misses later fixes like unescape or HTML restore.

Forgetting per-document state

Example: an extension that collects ids or footnotes but never calls md.registerExtension(self).

Why it hurts: Markdown.reset() will not clear it, so a second convert() on the same instance inherits old data.
